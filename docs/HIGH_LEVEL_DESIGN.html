Jobscan: High-Level Design

A local-first job search tracker for one user, running on a Mac. It finds roles, filters and scores them against a CV, helps modify the CV and cover letter, and tracks applications. Nothing runs in the cloud except calls to third-party services.

3. Design choices

Local-first

  • One user, one Mac, no hosted server.
  • The web app binds to 127.0.0.1, so no login is needed.
  • CV and notes stay on disk; only the text needed for a call goes to an LLM.

Simple stack

  • Python, Flask, Jinja2, SQLite.
  • No queue, no Redis, no front-end build.
  • Easy to run, back up (one file) and debug.

Batch plus on-demand

  • Scans and scoring are CLI jobs, daily via launchd.
  • The web app reads the database and runs single-role actions (score, modify CV).

Human in the loop

  • AI proposes; you approve every CV and letter change.
  • Email Sync proposes status changes; you accept or reject.
  • Re-scoring happens only on purpose.

5. Data and storage

SQLite (one file)

  • Roles: roles, phrases, run history, skipped titles.
  • CV: cv, cv_chunks, cv_files (original .docx), cover_templates.
  • AI: ai_fit (verdicts), ai_calls (log), role_scores, role_fit.
  • Documents: tailor_requests.
  • Email: sync_updates, sync_seen, sync_state.
  • Other: config, sites_companies, langfuse send log.

Reliability

  • WAL mode with a 10 second busy timeout, so the web app and a scan can share the file.
  • Numbered migrations; the app refuses a newer database than it knows.
  • Run lock: one scan at a time, web app holds a shared lock.

Secrets

  • Keys come from terminal variables (MISTRAL_API_KEY, GROQ_API_KEY, JOBSYNC_APP_PASSWORD).
  • The daily job reads the scoring key from the macOS Keychain.
  • Config stores only the variable name, never the value.

6. Caching and de-duplication

There is no cache server. Reuse is done inside SQLite, which is enough for one user.

7. Key flows

Daily scan and score

launchd→scheduled-run (lock)→LinkedIn / Naukri / company pages→dedupe + store roles→fetch descriptions→fit filter→Mistral verdict (new roles only)→SQLite

Review a role

Roles list→click row→panel fetch (HTML fragment)→edit status, notes, rating (autosave)→SQLite

Modify CV or cover letter

Modify button→request row (preparing)→Groq proposes edits→you review each change→new Word file→Modification History

Email Sync

Sync button / while serving→Gmail IMAP (read-only)→match to roles→proposed change queue→you accept or reject

Quality check

Your Good / Poor ratings→Eval compares with AI→optional push-traces to Langfuse

10. Security, privacy and failure handling

Security

  • Local-only binding; no inbound access.
  • Keys never stored; Gmail access is read-only.
  • Uploads limited to Word files, size-capped.
  • Redirect targets are checked (safe_next); links are checked (safe_link).

Privacy

  • CV text goes only to the scoring and modification providers.
  • Langfuse never receives the CV; role text only if Config allows.

Failure handling

  • A failed AI call is logged and the role stays unscored.
  • Rate limits stop a run with a clear note; the next run resumes.
  • A failed Langfuse upload is simply repeated later.
  • Each source failure is a plain-words reason, not a crash.

11. Limits and next steps

  • Single user and single machine by design; sharing it or moving it to a server would need login, a networked database and a job queue.
  • Scheduling is macOS only (launchd).
  • Free LLM plans cap throughput; Groq's 8,000 tokens a minute is the likely first bottleneck for CV edits.
  • Planned: Indeed and iimjobs as sources (requirements not yet written).
